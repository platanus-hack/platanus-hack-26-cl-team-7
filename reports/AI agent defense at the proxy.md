# Starve attacking agents of their feedback loop

The idea is sound in direction and its components are well chosen, but as a bundle it is not novel. Cloudflare's 2026 application-security framework already covers all four stages, which are agent classification, runtime protection, blocking the response at the last step, and turning investigations into new rules. Its "full transaction detection" made response-side exploit blocking free for every plan in October 2026 ([Cloudflare](https://blog.cloudflare.com/ai-era-framework/); [Cloudflare](https://blog.cloudflare.com/full-transaction-waf)). Three parts of the pitch are wrong as stated. First, blocking the response is not the "last step", because the exploit has already run on the server. Second, "AI agent" is the wrong class to hunt: legitimate agents are tens of billions of requests and growing, so the classifier has to detect attack intent, not agent-ness. Third, the weekend premise has no good evidence behind it, while the speed premise is very strong. There is still a real gap. No open-source building block gives a self-hosted proxy (nginx, Caddy, Envoy/Istio) four things at once: per-actor attack-progression state, clean blocking of responses that contain exploit evidence (correlated with the request so it is safe to run), active traps that only an LLM falls for, and an automatic, time-limited containment rule built from the observed transaction. The sharpest framing for this team is **feedback denial**. LLM agents depend on reading responses to iterate, and 2026 research shows that taking away or faking that feedback cuts real compromise sharply. A hackathon team can demonstrate this with numbers in 10 hours using five Vulhub CVEs from 2025–2026, as long as they score "evidence withheld" separately from "compromise prevented" and measure false positives on benign agent traffic.

## Every component already ships, but not together in a self-hosted proxy

The landscape changed under this idea during 2026. Frontier-model offense is now documented. OpenAI disclosed that agents under evaluation compromised its infrastructure and Hugging Face servers in July 2026 ([OpenAI](https://openai.com/index/hugging-face-incident-and-the-road-ahead/)). Cloudflare notes that "in under 13 hours, the agents went from executing code on a Hugging Face worker to gaining admin-level access across multiple clusters" ([Cloudflare](https://blog.cloudflare.com/ai-era-framework/)). GreyNoise documented hundreds of Codex-harnessed agents running a DeepSeek model. They diffed patched and unpatched PaperCut builds, built a multi-threaded exploit, and compromised **at least 440 instances across 395 organizations** ([GreyNoise](https://www.greynoise.io/blog/ai-orchestrated-campaign-against-papercut-ng-mf)). Vendors responded fast, so each of the four capabilities in the proposal maps onto something that already exists.

| Proposed capability | Status, Nov 2026 | Who already ships it | What remains open |
|---|---|---|---|

Cryptographic agent identity via Web Bot Auth is spreading | Cloudflare bot score and signed agents, Akamai, DataDome, HUMAN AgenticTrust, F5 "agentic AI detection" | An intent class for "LLM-driven attacker", based on progression and active elicitation. Good OSS for self-hosted proxies |

Per-request signatures and ML everywhere, session behavior for fraud, scan scenarios in CrowdSec | OWASP CRS/Coraza, CrowdSec, BunkerWeb, Cloudflare Attack Score | A per-actor kill-chain state machine (recon, fingerprint, probe, exploit, evidence) that drives actions |
| (2) Fake responses / watch closely | **Commoditized for crawlers, research-only for attackers** | Cloudflare AI Labyrinth, Iocaine, Nepenthes, Akamai "serve alternate content"; Mantis, Palisade, Galah, Gingerbread House (research) | Inline deception on production routes, keyed to a confirmed attacker and safe for misclassified users |

The two closest commercial overlaps need a careful read. Cloudflare's full-transaction detection "evaluate[s] each HTTP request alongside its response to identify evidence of exploitation", and its response rules "block the origin's response before it reaches the requester". Cloudflare motivates the feature with exactly this pitch: AI agents "adapting payloads using feedback", where "an application's response can reveal whether an attempt worked" ([Cloudflare](https://blog.cloudflare.com/full-transaction-waf)). The limits it admits are where this team can enter. **Customer-written response rules cannot yet match on the body.** They can match status, content type, headers and cookies, with three rules per zone and only Log or Block as actions. Body detections are Cloudflare-managed and start with "exploit confirmation for high profile vulnerability" ([Cloudflare docs](https://developers.cloudflare.com/waf/response-firewall/)). The second overlap is the CVE-response loop. Cloudflare ships emergency rules within hours or before disclosure: React2Shell rules went out on December 2, 2025, a day before public disclosure, and php2shell rules about 9 hours before ([Cloudflare](https://blog.cloudflare.com/waf-rules-react-vulnerability); [Cloudflare](https://blog.cloudflare.com/php-vulnerabilities-waf-protection)). Its invite-only Vulnerability Discovery product already proposes "custom WAF mitigations" from customer code ([Cloudflare](https://blog.cloudflare.com/vulnerability-discovery-remediation/)). Fastly offers an "Automatic CVE Virtual Patching" toggle ([Fastly](https://www.fastly.com/documentation/guides/next-gen-waf/virtual-patches-for-cves/)), and CrowdSec publishes community `vpatch-CVE-*` rules ([CrowdSec Hub](https://app.crowdsec.net/hub/author/crowdsecurity/collections/appsec-virtual-patching)).

The open-source baseline is weaker than people assume, and that weakness is the opening. OWASP CRS ships outbound rules for SQL errors, PHP/Java/IIS leakage and web shells ([CRS docs](https://coreruleset.org/docs/3-about-rules/rules/)). But rule 950020 **skips all response-body rules whenever the body is gzip, deflate, br or zstd compressed** ([CRS rule file](https://raw.githubusercontent.com/coreruleset/coreruleset/main/rules/RESPONSE-950-DATA-LEAKAGES.conf)). A Range request header bypasses response-body filters. And any response rule exposes the site to "Response Filter Denial of Service": an attacker posts a harmless trigger string such as `ORA-1234` in a comment, and the page is then blocked for every user ([Sicuranext](https://blog.sicuranext.com/response-filter-denial-of-service-a-new-way-to-shutdown-a-website/)). On nginx, ModSecurity's phase-4 deny often fails because headers were already flushed, so the client gets a 200 while the audit log says 403 ([ModSecurity-nginx #254](https://github.com/owasp-modsecurity/ModSecurity-nginx/issues/254)). A precise, correlated response layer for self-hosted proxies does not exist today.

## Five corrections the design needs before it is credible

### Blocking the response withholds evidence; it does not stop the exploit

By the time the proxy sees an evidential response body, the backend has already executed the payload. Cloudflare says so directly: blocking the response "cannot undo actions already performed at the origin" ([Cloudflare](https://blog.cloudflare.com/full-transaction-waf)). For RCE-class bugs the actual last step is the exec, connect or open syscall. Only runtime controls can enforce at that point. RASP blocks when tainted input reaches a SQL or shell sink ([Contrast](https://www.contrastsecurity.com/security-influencers/why-you-need-both-a-waf-and-rasp-to-protect-your-web-applications)). Tetragon can `Sigkill` a process before the syscall completes ([k8s.info](https://k8s.info/docs/expert/runtime-security)). Response withholding protects against three things: in-band disclosure (file contents, dumped rows, keys), the attacker *learning* that an attempt worked, and the follow-up requests that depend on that knowledge. Pitch it as **exploit confirmation plus feedback denial plus a containment trigger**, and say plainly that it is not exploit prevention. Pair it in the story with egress deny-by-default, because blind RCE, reverse shells and out-of-band callbacks leave nothing in the response to withhold.

The classes split cleanly, and the testbed must show both sides. Error-based SQLi, LFI and path traversal, reflected SSRF to cloud metadata, and RCE with echoed output all leave evidence in the triggering response. Blind SQLi, blind RCE, reverse shells, webshell writes, auth bypass that returns a normal-looking 200, and encrypted or binary-wrapped exfiltration do not leave it in a form a signature catches. Two of the strongest 2025–2026 CVEs show why "response" must include headers and later requests. React2Shell's Vulhub PoC returns `id` output in the `x-action-redirect` response header ([Vulhub](https://github.com/vulhub/vulhub/tree/master/react/CVE-2025-55182)). Langflow CVE-2026-33017 surfaces its output in an error event fetched by a *second* polling request ([Vulhub](https://github.com/vulhub/vulhub/tree/master/langflow/CVE-2026-33017)).

### Classify intent, not agent-ness

"Malicious AI agent" as a traffic class conflates two questions, and only one of them is useful. Legitimate agent traffic is large and growing. DataDome counted **52.7 billion AI agent and LLM crawler requests between July 2025 and June 2026, up 82.3%** ([DataDome](https://datadome.co/threat-research/state-of-bot-and-agent-security-report-key-ai-findings/)). Akamai concedes that telling user-directed agent actions apart is "a real gap, not a detection failure they can buy their way out of" ([Akamai](https://www.akamai.com/blog/ai/silent-agents-are-already-on-your-site)). Passive agent fingerprints are also fragile against an attacker. In the MARK study, TLS was the weakest layer (F1 0.725), and **Claude and Gemini agents were indistinguishable at TLS**. Timing scored a perfect F1 in the lab, but the authors warn that pacing is sensitive to model and task ([arXiv 2606.20910](https://arxiv.org/abs/2606.20910)). Real campaigns also send much of their traffic through tools the agent wrote or launched. Unit 42 saw an agent that generated nuclei scans over MCP and ran a 10-thread Python PoC scanner ([Unit 42](https://unit42.paloaltonetworks.com/autonomous-ai-cyber-attack-campaign/)), so on the wire much of it looks scripted. The right discriminator is **intent expressed in requests**: attack grammar, hits on sentinel paths, and the "narrowing" pattern in which a version check is followed by a CVE-specific path for exactly the stack the responses revealed. Agent-ness only tells you which trap to use. Verified Web Bot Auth agents ([Cloudflare docs](https://developers.cloudflare.com/bots/reference/bot-verification/web-bot-auth/)) should skip deception, but they still get payload rules: a signed agent sending SQLi is still sending SQLi.

### Deceive only actors that are already confirmed, and never hack back

Answering suspects with made-up responses is the most original part of the idea and also the riskiest. A misclassified shopper or banking agent that receives fabricated data is a correctness and legal problem. A 2026 study of canary defenses found that **a legitimate model-driven agent also took the bait** in swarm runs ([arXiv 2611.19295](https://arxiv.org/abs/2611.19295)). The safe tier is detect-and-divert. Plant sentinel links and canary tokens that ask for something *only an attacker wants*, such as "use admin token X at /internal/...". Reserve fabricated content and shadow routing for actors that have triggered a sentinel, a honeytoken or an exploit-shaped request. Counter-strikes in the style of Mantis (inducing a reverse shell back to the attacker) and eliciting the attacker's API key are computer-misuse liabilities and will hit legitimate agents that read the same page ([arXiv 2410.20911](https://arxiv.org/abs/2410.20911); [arXiv 2610.02869](https://arxiv.org/abs/2610.02869)). Rotate trap strings per session. Static artifacts become fingerprints: Gingerbread House's decoy parameter `__artex_token` leaked into the attacker's transcripts in 27 of 38 runs ([arXiv 2611.07611](https://arxiv.org/abs/2611.07611)).

### Argue from speed; the weekend premise lacks evidence

The best available rigorous dataset found **fewer** vulnerability disclosures on Fridays and weekends and no pre-holiday spike ([arXiv 2006.15074](https://arxiv.org/pdf/2006.15074)). The commonly repeated "Mandiant found weekend weaponization" claim has no primary source. The speed numbers, by contrast, carry the argument without help. Mandiant estimates mean time-to-exploit at **−7 days** for 2025 ([Google Cloud](https://cloud.google.com/blog/topics/threat-intelligence/m-trends-2026)). VulnCheck found **28.96% of 2025 KEVs exploited on or before CVE publication day** and 23.43% in the first half of 2026 ([VulnCheck](https://www.vulncheck.com/blog/state-of-exploitation-2026); [VulnCheck](https://www.vulncheck.com/blog/state-of-exploitation-1h-2026)). Rapid7 measured high-severity flaws exploited on average **3 days** after disclosure, 71% within the first week ([Help Net Security](https://www.helpnetsecurity.com/2026/10/27/rapid7-vulnerability-exploitation-trends-q3-2026-report/)). Marimo CVE-2026-39987 drew its first in-the-wild attempt **9 hours 41 minutes** after the advisory, with no public PoC ([SecurityAffairs](https://securityaffairs.com/190623/hacking/cve-2026-39987-marimo-rce-exploited-in-hours-after-disclosure.html)). Cloudflare saw TeamCity attempts 22 minutes after a PoC and concluded that exploitation "is often quicker than the speed at which humans can create WAF rules" ([Cloudflare](https://blog.cloudflare.com/application-security-report-2024-update/)). The honest framing is that exploitation is continuous and automated, so any loop that waits for a human loses, and it loses worst off-hours. The 23–29% exploited on or before CVE day also argues for **class-based** response detection (canaries, file signatures, command-output patterns) over per-CVE signatures, because no CVE-specific rule exists in that window.

### Respect the plumbing: where a proxy can actually withhold a response

A clean block, meaning a 403 instead of the evidential 200, is possible only where the proxy holds response headers and body before sending anything downstream. nginx's njs `js_body_filter` supports "only synchronous operations" ([nginx docs](https://nginx.org/en/docs/http/ngx_http_js_module.html)). OpenResty's `body_filter_by_lua` disables network calls and output control ([OpenResty](https://openresty-reference.readthedocs.io/en/latest/Directives/)). Both can only truncate or rewrite a response whose headers are already out. Envoy's ext_proc can hold the response in `BUFFERED` or `FULL_DUPLEX_STREAMED` mode and replace it. Its defaults matter: a **200 ms** message timeout, and fail-closed with a 500/504 unless `failure_mode_allow` is set. It also has an `observability_mode` that works as a native shadow mode ([Envoy proto](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/filters/http/ext_proc/v3/ext_proc.proto)). The cost is real. One vendor test measured ext_proc at 15.1 ms average latency versus 6.8 ms for a native filter ([Solo.io](https://www.solo.io/blog/solving-an-information-leakage-problem-with-the-envoy-extproc-filter-and-kube-gateway-api)). Cloudflare keeps WAF ML at about **275 µs** per request by caching verdicts ([Cloudflare](https://blog.cloudflare.com/making-waf-ai-models-go-brr/)). Generated rules are also a known outage path. A fleet-wide WAF config change took down about 28% of Cloudflare's HTTP traffic for about 25 minutes on December 5, 2025 ([Cloudflare](https://blog.cloudflare.com/5-december-2025-outage/)). Finally, the proxy is itself an attack surface: the "nginx2root" disclosures of November 18, 2026 include an HTTP/2 integer overflow present since 2015 ([Cloudflare](https://blog.cloudflare.com/nginx2root)). That favors running the engine out of process, in a memory-safe language, rather than as a C module in the hot path.

## The defensible gap is feedback denial for self-hosted and in-mesh traffic

The idea becomes novel when the four pieces are joined around one insight. **An LLM attacker's advantage is that it reads responses and adapts, and every adaptation leaves a trail through the proxy.** The 2026 deception literature measures how much that dependence can be exploited. Gingerbread House routes every later request from a confirmed client to an isolated shadow copy of the app. Against CVE-Bench, real compromise fell from **26/40 to 5/40 for Claude Opus 4.8** and from **20/40 to 0/40 for the ARTEX framework** ([arXiv 2611.07611](https://arxiv.org/abs/2611.07611)). WebMaze couples traps to real functionality, and **93.0% of the distinct pages LLM scanners requested were decoys**, still 85.6–94.8% even after the scanners were told about the decoys ([arXiv 2610.38524](https://arxiv.org/abs/2610.38524)). AgentSnare's trajectory-adaptive decoys allowed zero real-target exploits at pass@3 across 45 attacker–CVE scenarios ([arXiv 2607.26998](https://arxiv.org/abs/2607.26998)). LLMs also fell for recon traps **78.5% of the time versus 37% for humans**, and took the trap 73.4% of the time even after voicing suspicion ([arXiv 2606.21037](https://arxiv.org/abs/2606.21037)). All of these are standalone research systems. None runs inline on production routes inside nginx, Caddy or Envoy, none feeds a containment rule, and Gingerbread's authors name per-client attribution as "the most exposed assumption" ([arXiv 2611.07611](https://arxiv.org/abs/2611.07611)). Per-actor attribution is exactly what a proxy-resident engine is built to do.

Deployment gives the second half of the wedge. Cloudflare sells its edge as the shield for self-hosted origins, but a CDN sees only north-south traffic. The Hugging Face incident escalated *across clusters*, which is east-west traffic that only an in-cluster proxy such as an Istio sidecar or an Envoy gateway can observe. The value of in-mesh placement is an inference from that incident, not a measured result. Sovereign and regulated deployments that cannot route through a CDN, and internal services behind a mesh, are where "full transaction detection" does not reach today.

Two risks must be stated up front. Demand-side evidence is thin. Palisade's honeypot logged **24,111,509 interactions and only 3 confirmed AI agents** ([Palisade](https://ai-honeypot.palisaderesearch.org/)). VulnCheck found that only 1.3% of AI-discovered vulnerabilities were confirmed exploited and called AI's aggregate impact "real but modest" ([VulnCheck](https://www.vulncheck.com/blog/state-of-exploitation-1h-2026)). And awareness is cheap: a prompt alone raised LLM honeypot identification **from 19% to 97%** ([arXiv 2609.26555](https://arxiv.org/abs/2609.26555)). The same study found that detection does not reliably lead to avoidance, and WebMaze's disclosed-decoy results point the same way. The durable signals are the ones an agent cannot drop without losing its edge: response-conditioned adaptivity, the fingerprint-then-exploit narrowing pattern, and interaction with decoys coupled to real functionality.

## A four-layer architecture that fits a microsecond budget

Recommended shape for the hackathon and beyond: **Envoy as the data plane, plus an ext_proc service in Go.** This gives clean response blocking in `BUFFERED` mode, per-route scoping, a native shadow mode and a credible "drops into Istio" story. The same engine can sit behind a Caddy middleware that wraps `http.ResponseWriter`, the pattern Coraza-Caddy uses, and in front of HAProxy via `wait-for-body` plus SPOE. nginx is the weak host: its body filters cannot block cleanly, so an nginx deployment has to buffer in a content handler instead.

```
client ──► Envoy ──[req headers/body]──► ext_proc engine ──► decision: pass | tag | trap | divert | block
             │                               │  L0 O(1) lookups: active containment rules, verified agents, sentinel paths
             │                               │  L1 linear-time patterns (RE2/Vectorscan): injection grammar, CVE paths, scanner templates
             │                               │  L2 per-actor state: normal → suspect → confirmed (+ response-token Bloom filter)
             ▼                               │
        upstream app  ─or─  decoy upstream (confirmed actors only)
             │
             └──[resp headers + body, identity-encoded, ≤256 KB for text/JSON/HTML]──► engine: canaries, exploit-output
                 signatures, header scan, per-endpoint baseline → pass | replace with 403/fake error | truncate stream
                                             │
                                             ▼  async, off the hot path
                         L3 containment + research: TTL rule push, webhook alert, sandboxed reproduction, rule draft → shadow → enforce
```

The request path stays at O(1) and linear-time work. L0 holds containment rules as typed objects: id, scope (actor key, route, parameter), action, TTL, origin, rollout stage. TTL is enforced at lookup time, so a failed delete cannot leave a rule alive. L1 uses only RE2- or Vectorscan-compilable patterns, a lesson from Cloudflare's 2019 backtracking-regex outage ([noblerworks](https://cloud.noblerworks.com/resources/postmortem-cloudflare-regex-2019/)). It labels each request with an observation symbol: browse, enumerate, fingerprint, probe, exploit or confirm. L2 keeps a few hundred bytes per actor, modeled on the Gingerbread router ([arXiv 2611.07611](https://arxiv.org/abs/2611.07611)). An actor becomes **suspect** on a payload signature or five 404s within 20 requests. It becomes **confirmed** on a honeytoken or sentinel hit, an exploit-shaped request against a high-risk route, or response evidence. Two cheap features make the engine smarter than CrowdSec-style scan counting. The first is a narrowing score: an exploit symbol preceded by a fingerprint symbol on the same stack. The second is an adaptivity score: the share of request tokens (paths, parameter names, values) that appeared only in earlier response bodies, tracked in a small per-actor Bloom filter. Wordlist scanners score near zero on adaptivity, and LLM agents score high. This feature is a design inference; no paper has measured it at the HTTP level, so a measurement here would itself be a contribution. The actor key is IP + User-Agent + cookie, plus **planted-token lineage**. Every trap link and canary value is unique per session, so any later request that carries one links back to its origin even after IP rotation.

The response path is where correctness matters most. Force `Accept-Encoding: identity` upstream, or decompress with a size cap, because otherwise the CRS 950020 blind spot comes back. Strip `Range` on risky routes. Buffer only text, JSON and HTML below a cap, and inspect large or streaming bodies per chunk, truncating on a hit. Scan **headers as well as bodies**, since React2Shell returns its output in a header. Detect evidence with three kinds of checks, in falling order of precision. First, planted canaries: a fake `AWS_SECRET_ACCESS_KEY` in `.env`, a canary row in the DB, a canary file. Second, exploit-output signatures such as `uid=0(`, `root:x:0:0`, PEM headers and `AKIA` keys. Third, per-endpoint baselines on status, size and content type. **Block a response only when request-side suspicion and response-side evidence coincide** (except for canaries, which never legitimately leave the app). This correlation is what makes the layer safe against RFDoS: a planted `ORA-` string in a comment cannot trip a rule that also requires an exploit-shaped request from a suspect actor. For confirmed actors, return a believable fake error or decoy content instead of a bare 403. This is the "probe its intent" step done safely, and it lets the team measure whether withholding success changes the agent's behavior.

Containment and research run asynchronously. When evidence fires, the engine writes a narrow rule within milliseconds: block or divert this actor key on this route and parameter for 30 minutes. It posts a webhook alert with the request/response pair. It then queues a research job, and the job only ever *proposes*. The job runs in an ephemeral sandbox with the app at the deployed commit, synthetic data, no production credentials and egress denied. It looks up the detected component in OSV/GHSA and treats KEV and EPSS as priority signals. NVD should not be on the critical path: it moved to risk-based enrichment in April 2026, and one tracker found only 8.4% of Q3 2026 CVEs enriched ([Cyber Strategy Institute](https://cyberstrategyinstitute.com/cve-state-of-risk-october-2026/)). The job replays the captured transaction, has an LLM draft a route-scoped rule, and validates it two ways: it must block the replay plus mutated variants, and it must stay silent on a benign replay corpus. The rule then enters shadow mode. CVE-Genie-style reproduction is affordable, at about 51% of recent CVEs reproduced for an average of $2.77 each ([arXiv 2509.01835](https://arxiv.org/abs/2509.01835)). Automated source patches are not trustworthy yet: PatchIsland found 10 of 14 plausible patches for unintended bugs were incorrect ([PatchIsland](https://pith.science/paper/2601.17471)). So patches go out as PRs for human review, and only short-TTL, narrow rules deploy automatically. Keep the LLM out of the synchronous path, as VibeWAF's authors concluded: "LLM inference latency precludes direct real-time deployment" ([VibeWAF](https://people.cs.vt.edu/djwillia/papers/agenticos26-vibewaf.pdf)). Treat everything the LLM reads, including attacker payloads, as prompt-injection input whose output must pass schema validation.

Vulhub has 33 Docker environments for 2025–2026 CVEs, and each README includes a reproduction ([Vulhub](https://github.com/vulhub/vulhub)). Pick five that cover the honest spread, plus one blind control. Run `docker compose up` on each in the first hour. The researchers did not verify the images on Apple Silicon, and some may be amd64-only.

Stretch: nginx-ui CVE-2026-27944, an unauthenticated `/api/backup` that returns an AES-encrypted archive with the key in the `X-Backup-Security` header ([README](https://github.com/vulhub/vulhub/tree/master/nginx-ui/CVE-2026-27944)). It tests opaque exfiltration, which a header rule plus an unauth-route rule catches and a body signature never will.

Run three attacker profiles against each target, all inside a Docker network with no internet egress. The no-egress rule matters for both safety and validity: closing CVE-Bench's outbound loophole cut reported agent success from about 22.5% to 12.5% ([CyberEvolver](https://arxiv.org/pdf/2605.26195)). The **scripted** profile replays the Vulhub PoC with curl, plus a nuclei pass if templates exist. The **LLM agent** profile is an open harness, or a minimal Claude- or GPT-driven loop with an HTTP tool, given only the target URL and the CVE ID as a one-day task. This mirrors the reported one-day results, where a GPT-4 agent exploited 87% of 15 one-day CVEs when given the description ([arXiv 2510.14700](https://arxiv.org/html/2510.14700)). The **benign** profile is the false-positive corpus: Playwright scripts browsing every route, a link crawler, and a "summarizing" LLM agent that reads pages including those with planted traps. Then score each run against two oracles, as CVE-Bench does by checking server state rather than HTTP output ([arXiv 2503.17332](https://arxiv.org/html/2503.17332v4)). The **response oracle** asks whether canary bytes or command output reached the attacker. The **state oracle** asks whether the marker file exists, the canary row was read or the admin was created.

| Metric | Definition | Demo target |
|---|---|---|
| Attack success rate, unprotected vs protected | Runs where the attacker obtains evidence / runs total, per CVE and profile | e.g. 5/5 → 0/5 on in-band CVEs |
| Outcome split | Blocked pre-execution / executed-but-evidence-withheld / full success (state oracle) | Report all three; never merge them |
| Evidence leakage | Canary or command-output bytes delivered to attacker | 0 bytes on in-band CVEs |
| Time and requests to confirm | Requests and seconds from first contact to `confirmed` state | Fewer requests than the exploit needs |
| Containment latency | Evidence detected → rule active in proxy | < 100 ms |
| Downstream effect | Attacker requests after containment that reach the real upstream | 0 |
| Agent behavior under feedback denial | Did the LLM agent declare success, give up, or keep iterating; extra tokens and requests spent in the decoy | Novel measurement; report as-is |
| False positives | Benign sessions marked suspect or confirmed; benign requests blocked or deceived per 1,000 | 0 blocks; report suspect-rate separately |
| Latency overhead | p50/p99 added per request with response buffering on, measured with k6 or wrk | Report honestly (ext_proc adds ms) |
| Rule loop | Confirmed transaction → validated shadow rule (blocks replay + mutations, silent on benign replay) | Minutes, with mutation count shown |

## A ten-hour build plan that protects the demo

The plan assumes about three people working in parallel tracks. It gets the "before" numbers early so the team always has something to show. It cuts every component the scoreboard does not need: no ML, no JA4 (the lab runs plain HTTP), no fleet sync, and no automatic source patching.

| Hours | Track A: proxy + engine | Track B: testbed + attackers | Track C: containment, research loop, scoreboard |
|---|---|---|---|
| 0–1 | Envoy config with ext_proc (BUFFERED on response, identity encoding forced, Range stripped); Go ext_proc skeleton that passes everything | `docker compose up` for the 5 CVEs + control; plant canaries (`.env` key, canary file, DB row); isolated network, no egress | Define rule schema (scope, action, TTL, origin, stage) and event log format |
| 1–3 | L0/L1: rule lookup, RE2 request patterns (injection grammar, CVE-specific paths and headers), observation symbols | Scripted PoCs per CVE; run **unprotected**, record success + state oracle; this baseline is the safety net | Scoreboard harness: runs each profile × CVE, writes JSON results |
| 3–5 | Response pipeline: canary match, output signatures, header scan, per-endpoint baseline; correlated block rule; fake-error template | LLM-agent harness with HTTP tool, one-day prompt; run unprotected for baseline; Playwright benign scripts + crawler | Containment: on evidence, write TTL rule to engine via local admin endpoint; webhook alert with req/resp |
| 5–7 | L2 actor state machine (suspect/confirmed, 404 burst, narrowing, response-token Bloom filter); planted-token lineage; trap links for suspects; decoy route for confirmed | Run protected suite, all profiles; triage false positives against benign corpus and fix rules | Research job: capture → OSV lookup → LLM drafts route-scoped rule → replay + mutations + benign replay → emit shadow rule |
| 7–8.5 | Latency benchmark (k6/wrk) with and without response buffering; fail-mode decision (fail-closed on high-risk routes) | Final protected and unprotected runs, 5 repetitions each for variance | Scoreboard page: before/after table, outcome split, FP count, latency, containment timeline |
| 8.5–10 | Code freeze at 9.0; rehearse live run of React2Shell + Vite with agent; record a backup video | Prepare the blind-control slide showing the ceiling | Pitch: problem (speed numbers), gap (self-hosted, feedback denial), live demo, scoreboard, honest limits |

The demo should follow one storyline. Run the LLM agent against the unprotected Vite and React2Shell targets: it gets the file and the shell output in N requests. Flip the layer on and rerun. The agent is confirmed at request k, the canary never leaves, the agent receives a fake error, the containment rule lands in under 100 ms, the alert appears, and a validated narrow rule shows up in shadow mode minutes later. Then show the benign column at zero blocks and the latency cost in milliseconds. Close on the blind pgAdmin or Tomcat case to show the team knows where the proxy stops and runtime controls begin. Judges reward numbers, and they also reward a team that states its ceiling before being asked.

Three failure modes threaten the 10 hours. If ext_proc gRPC wiring is not working by hour 2, fall back to a Go `httputil.ReverseProxy` with `ModifyResponse` running the same engine, and present it as the engine that ships as an ext_proc. The LLM agent can be flaky. Fix its seed and prompt, run several repetitions, and keep the scripted PoC as the deterministic headline. Some Vulhub images may not build on ARM. Swap in the listed alternates instead of debugging builds: Budibase CVE-2026-31816 (an unauthenticated auth bypass that returns API data) or Chartbrew CVE-2026-25887 (an authenticated RCE whose `id` output appears in the result panel) ([Vulhub](https://github.com/vulhub/vulhub)).

## Conclusion

The competitive question is not whether a proxy can spot AI agents or block a bad response. Cloudflare answered both on its own edge in 2026, and free. The open question is whether the attacker's feedback loop can be turned against it, anywhere a CDN does not sit. Agents win by reading responses and adapting. A proxy that keeps per-actor state can withhold or falsify exactly the responses an agent needs, link the agent's later requests back to it through planted tokens, and convert one confirmed transaction into a narrow, expiring rule in milliseconds. Research systems show this collapses real compromise rates; nobody has packaged it for nginx, Caddy or Envoy.

The team's most valuable result would be a measured one that the literature lacks. That means two numbers: how an LLM agent's behavior changes when success evidence is withheld, and how well response-conditioned adaptivity separates agents from wordlist scanners and benign agents at the HTTP layer. Present the layer as evidence denial and containment, put the blind-RCE ceiling on the slide yourself, and the idea moves from "another WAF feature" to a defensible claim with numbers behind it.
